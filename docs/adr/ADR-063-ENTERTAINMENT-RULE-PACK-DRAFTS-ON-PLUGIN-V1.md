# ADR-063：用 Plugin API v1 的配置与确认流程接入娱乐规则包

- 状态：Accepted
- 日期：2026-09-30
- 阶段：Phase 6.5

## 背景

娱乐模式已具备规则无关的世界/角色、剧情树、可信骰子、规则检定、状态补丁和检查点。学习插件也已冻结 Plugin API 1.0.0。如果按玩法 ID 在核心回合服务中不断增加条件分支，扩展会改变已验证的核心流程。首个娱乐规则包需要成为真实可用的 Activity，同时保持既有 v1 契约。

## 决策

- 使用静态 GameRulePackRegistry 注册描述符、输入 Schema 与纯会话构建器；与 Manifest/Activity 的归属、版本和能力声明交叉验证。
- 轻量冒险只申请现有 `storage.read-write`，通过 Capability Gateway 保存配置；草稿构建为确定性操作，不伪装成 `model.generate`。
- 中立草稿带来源信息和原有 `createGameSessionSchema` 内容，构建时先完整验证，再保存配置。
- 由宿主所有的确认组件在用户点击后调用核心 GameSession API。规则包服务只依赖 Gateway，不能取得核心 Repository。
- Prompt Layer 编译为世界规则，角色属性编译为角色卡；声明引用既有工具/状态 Schema。核心回合服务通过原有装配读取规则，不识别具体规则包 ID。
- Web 与 Android 使用相同预编译 React Activity；仅在两端路由注册入口。
- 重用现有 JSONB 隔离存储、乐观锁、配额与审计，不增加数据库迁移或 v1 能力种类。

## 后果

新增兼容现有宿主契约的规则包只需要模块、注册和专属 UI。插件禁用不影响已创建的游戏，因为规则与角色已存入 GameSession；新增包仍随应用构建发布，第一方同进程 UI 不是第三方沙箱。

当前 ID/版本在草稿来源与可读世界规则中保留，没有新增核心外键。将来要按包查询/升级应增加结构化来源字段。新判定算法、动态工具、状态扩展和第三方代码执行不能只靠注册或 Prompt 获得能力，必须单独设计宿主契约。

## 验证

单元测试覆盖不同模板、替代包注册、归属和严格输入；真实 SQL 集成验证授权、隔离、冲突、预览无核心写入、显式确认创建与既有回合服务；移动视口 E2E 覆盖预览失效、单次创建、精确会话导航和授权恢复。
