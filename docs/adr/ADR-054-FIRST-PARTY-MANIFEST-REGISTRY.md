# ADR-054 第一方 Manifest Registry 先于插件执行

- 状态：Accepted
- 日期：2026-09-28
- 对应阶段：Phase 7.1

## 背景

项目已经明确需要背书和解题两个学习插件，但直接加载任意代码会同时引入权限、隔离、升级和移动端原生能力问题。Plugin API 也尚未被真实活动验证，不能过早承诺稳定 v1。

## 决策

1. Phase 7.1 只发现编译进仓库的第一方 Manifest，不提供上传、远程目录或代码执行入口。
2. Manifest 使用严格 Schema v1，声明规范版本、实验 Plugin API 半开范围、贡献与请求能力；未知字段、重复 ID 和无效清单逐项隔离。
3. Registry 将兼容性与启停分离。Manifest 声明不等于安装状态，更不等于权限；不兼容项保持可见但不能有效启用。
4. PostgreSQL `plugin_installations` 只保存用户、插件 ID、安装版本、状态和乐观锁版本。Manifest 与代码仍由应用发布物提供。
5. 当前宿主 API 为 `0.1.0`，在背书和解题均通过 Capability Gateway 完成前不冻结 v1。
6. “背书训练”和“解题训练”先以明确的 foundation 状态登记；启用只保存用户意图，不声称活动已经可用。

## 备选方案

- 直接采用 DeepSeek Harness 式一切皆插件：当前单用户产品会为通用框架付出过高复杂度，因此拒绝。
- 在数据库保存任意 Manifest 或代码：会把状态写入接口变成隐式安装入口，因此拒绝。
- 等背书功能完成后再抽象插件：容易让第一个活动直接依赖核心内部实现，增加第二个插件接入时的返工，因此拒绝。

## 后果

- 用户已经能看到、启停和理解第一方插件边界，版本不兼容不会拖垮核心应用。
- Phase 7.1 本身不提供背书或解题活动；下一阶段必须通过 Capability Gateway 才能向插件开放任何核心能力。
- 第三方生态仍需独立解决签名、来源信任、沙箱、升级回滚和 UI 隔离，不能把第一方 Registry 误称为插件市场。
