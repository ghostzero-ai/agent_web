# ADR-030：任务领域模型与第一版时间规则

- 状态：Accepted
- 日期：2026-09-10

## 背景

项目需要在网页关闭后仍能按计划提醒用户。浏览器计时器受页面生命周期、休眠和移动端后台限制，无法成为可靠事实来源。后续还要支持普通提醒、AI 定时内容、执行重试和多实例部署，因此“用户计划”和“每次执行”不能混为一条记录。

## 决策

1. PostgreSQL 的 `scheduled_tasks` 保存用户计划，`task_runs` 保存每次计划执行。
2. 第一版仅提供 `once`、`daily`、`weekly` 三种结构化规则和 `reminder` 类型。
3. 第一版固定 `Asia/Shanghai`；服务端计算并保存 UTC `nextRunAt`，客户端仅负责采集用户输入。
4. `(task_id, scheduled_for)` 建立唯一索引，为 Scheduler 幂等提供数据库防线。
5. Task 使用递增 `version` 做乐观并发控制，避免电脑和手机互相静默覆盖。
6. Sprint 2.1 只管理计划，不在 Web 请求或浏览器中执行任务。

## 取舍

- 固定时区让个人版规则简单、可验证，但在多用户或旅行场景前必须加入用户时区与时区变更策略。
- 结构化规则不如任意 Cron 灵活，却能提供清晰 UI、严格校验和稳定的下一次时间计算。
- Task/TaskRun 两表增加了模型复杂度，但可以独立记录失败、重试、通知和历史，也为未来迁移到云端 Worker 保留边界。

## 被否决方案

- `setTimeout` / Service Worker 单独调度：设备休眠、页面关闭或浏览器回收后不可靠。
- 每分钟扫描并直接执行 Task：并发实例会重复执行，且没有独立的执行审计记录。
- 第一版直接接受 Cron：表达能力超出当前 UI 需求，校验和时区语义更难向个人用户解释。

## 后果

Sprint 2.2 必须以数据库事务、唯一 Run 和租约完成 claim；Sprint 2.3 的提醒 Worker 只能消费 TaskRun。若未来迁往云端，Web 与 Worker 可以更换部署位置而无需改变客户端任务格式。
