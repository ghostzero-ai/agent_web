# ADR-055：第一方插件只能通过受控 Capability Gateway 工作

- 状态：Accepted
- 日期：2026-09-28
- 对应阶段：Phase 7.2

## 背景

Phase 7.1 已能发现和启停背书、解题插件，但 Manifest 中的能力仍只是声明。若学习活动直接导入数据库、模型 Provider 或任务 Repository，插件禁用、授权、配额和审计都无法形成可信边界，也无法在未来替换为第三方沙箱。

## 决策

1. 插件声明、安装启用和用户授权是三个独立状态；能力按插件、用户和当前插件版本逐项审核。
2. 插件只能调用宿主静态注册的结构化 Adapter。浏览器没有通用能力执行端点，插件不会取得数据库连接、任意 SQL、模型密钥、网络客户端或核心 Repository。
3. 每次调用检查 Registry 兼容性、安装与版本、Manifest 声明、授权、前台用户动作或后台 Run ID，以及固定 UTC 日配额。
4. 插件 JSON 存储按 `userId + pluginId + key` 隔离，限制 Key、单值、条目数和总字节数，并用乐观锁处理并发写入。
5. 授权变化与每次调用均记录元数据审计；禁止把 Prompt、学习材料、存储值、模型输出或凭据写入审计。
6. Phase 7.2 只注册 `storage.read-write` Adapter。模型生成和任务草稿的具体输入 Schema 与核心领域复核留给 7.3/7.4，以避免在没有真实活动前冻结错误接口。
7. 禁用只使授权失效，不自动删除数据或授权记录；用户在禁用状态仍可撤销授权。插件版本变化要求重新审核。

## 备选方案

- 启用插件时一次性授予所有 Manifest 能力：用户无法理解或撤销单项高风险能力，因此拒绝。
- 为插件暴露通用内部 API、数据库或 SQL：无法保证数据隔离与领域规则，因此拒绝。
- 立即引入进程/容器沙箱：当前只有随应用发布并接受代码审查的第一方插件，成本高于近期收益，因此延后到第三方代码开放前。
- 在审计中保存完整输入输出：会复制私人学习材料和模型内容，因此拒绝。

## 后果

- 7.3/7.4 可以在不直接依赖核心数据库的情况下实现真实学习闭环，并用两个插件验证 Adapter 是否足够。
- 当前是第一方模块边界，不是恶意第三方代码的强隔离；同进程代码仍需代码审查和依赖规则。
- 权限、配额和审计成为可见产品能力，但用户授权尚未代表模型/任务 Adapter 已经可用。
