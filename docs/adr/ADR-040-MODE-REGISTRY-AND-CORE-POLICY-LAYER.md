# ADR-040：Mode Registry 与核心 Policy Layer

- 状态：Accepted
- 日期：2026-09-26

## 背景

项目需要同时支持专业回答、情感陪伴、反思提问和娱乐体验。如果每种能力各自拼接一段 system prompt，事实标准、隐私边界和工具权限会逐渐分叉，陪伴或角色扮演也可能意外降低专业回答要求。现有 Prompt Builder 只有 Persona、Memory 和 Conversation，数据库虽已有 `mode` 字段，但它尚未参与实际模型输入。

## 决策

1. 建立唯一 `ModeRegistry`，核心注册 `auto`、`professional`、`companion`、`reflection` 和 `entertainment`。模式定义包含目的、交互指令、事实标准、默认工具意图和持久化边界。
2. Prompt Builder 的固定顺序为：`Policy → Mode → Persona → Memory → Conversation`。Policy 由核心代码提供，模式、Persona、记忆、插件或用户内容都不能在结构上移动到它之前。
3. 核心 Policy 统一约束事实与不确定性、高风险回答、虚构/现实分离、间接 Prompt Injection 和敏感信息暴露。陪伴模式不得为了安慰歪曲事实，娱乐模式不得把世界内设定冒充为现实。
4. Mode 只声明交互协议和工具意图，不直接授予工具、数据库、网络或系统权限。实际工具授权仍由后续 Tool Gateway 和审批策略决定。
5. Registry 在注册时校验、复制并冻结定义，拒绝重复 ID 和未知查询，避免调用方在注册后篡改共享模式对象。
6. Core 3.1.1 只完成领域与 Prompt 装配。现有服务端会话会把持久化 mode 投影到客户端；旧记录或缺失字段回退到 `auto`。娱乐模式的数据库枚举迁移、模式切换 API 和 UI 留给 Core 3.1.2。

## “不可覆盖”的准确含义

这里的不可覆盖是软件结构保证：低优先级层不能替换、删除或排到 Policy 之前，注册模式也不能获得额外权限。LLM 对自然语言规则的遵循不是形式化安全边界，因此 Core 3.4 仍需通过对抗样例和评测测量事实、隐私与模式边界的实际遵循率。

## 后果

- 专业、陪伴和娱乐共享事实与隐私底线，同时可以拥有不同交互风格。
- Prompt 导出会自然显示 Policy 与 Mode 层，便于用户检查模型实际收到的指令顺序。
- 后续插件可以引用模式元数据，但不能依靠模式文本自行获取工具权限。
- 在 Core 3.1.2 完成前，用户界面仍使用 `auto`，不宣称娱乐模式已经可用。
