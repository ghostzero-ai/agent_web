# ADR-049：长期记忆采用服务端候选与显式确认

- 状态：Accepted
- 日期：2026-09-27
- 对应阶段：Phase 5.1

## 背景

项目早期的 Browser Storage 原型在会话达到阈值后，会把最近用户消息直接标记为 `fact` 并写入 `localStorage`；聊天随后把最近十条浏览器记忆全部注入 Prompt。该逻辑无法区分问题、临时请求、真实偏好和敏感资料，也缺少来源、确认、纠错与多端一致性。Phase 5 的陪伴和主动联系不能建立在这种不可信数据上。

## 决策

1. 新增 `memory_candidates` 和 `memory_items`。候选不是记忆；只有用户确认候选的事务才可以创建正式记忆。
2. 客户端只发送会话 ID 和消息 ID。服务端验证消息属于本地用户且角色为 `user`，再读取数据库正文，避免客户端伪造来源或让助手回答成为用户记忆。
3. Phase 5.1 使用高精度确定性提取：支持明确“请记住”指令、稳定偏好、长期目标和有限个人资料；包含问号、明显临时时间词、普通请求或疑似密钥的消息不产生候选。
4. 候选保存规范内容、原始证据、类型、敏感等级、置信度和提出原因。所有候选无论风险高低都进入 `pending`，由用户修改后确认或拒绝。
5. 确认操作锁定候选、校验版本和状态、检查重复、创建 `memory_items`，再把候选改为 `confirmed`；任一步失败都会回滚。拒绝只改变候选状态。
6. 停用 Context Compressor 的自动记忆写入和聊天对浏览器记忆的读取。Phase 5.2 完成相关性检索前，正式记忆也不会被无差别注入 Prompt。

## 未选择的方案

- 不让模型自由抽取并自动保存：开放式抽取容易把推断、情绪和临时上下文永久化，也需要额外评测后才能授权。
- 不允许客户端直接提交候选正文：正文必须来自已经持久化且所有权可验证的用户消息。
- 不实现低风险自动保存：当前单用户项目更重视可审查性；积累真实候选后再决定是否需要分级授权。
- 不在本阶段实现向量数据库：Phase 5.1 解决写入可信度，Phase 5.2 才根据实际记忆量验证关键词、全文或语义检索。

## 后果与回滚

长期记忆从隐式副作用变为可解释、可拒绝的用户操作，并为插件未来只能“提交候选”提供稳定边界；代价是需要一次确认且高精度规则会漏掉隐含信息。迁移 `0016_happy_bug` 可回滚，依次删除正式记忆和候选表；旧浏览器存储代码仍保留为兼容读取工具，但生产聊天不再读写它。
