# ADR-044：确定性 Response Verifier 与分支级检查结果

- 状态：Accepted
- 日期：2026-09-26

## 背景

Core 3.3 能把检索来源交给模型并保存行内引用，但“存在引用”不等于引用有效，也不能暴露回答缺少日期、引用编号编造或把推断写成事实等问题。再次调用模型进行自我评分会增加成本、延迟和新的幻觉来源，并且同一答案可能得到不稳定结论。

## 决策

1. 在模型流完成后、发送 SSE `done` 前运行服务端确定性规则引擎，不发起第二次模型请求，也不自动改写或阻断原回答。
2. Verifier v1 固定输出四项检查：
   - 引用完整性：`[Sx]` 是否对应本次检索结果，已检索回答是否遗漏行内引用。
   - 摘要支持度：引用附近断言与标题/搜索摘要是否存在可解释的中英文词面关联。
   - 时效标注：时效问题是否完成检索、具有引用并写明明确日期。
   - 推断边界：强推断语句是否缺少引用或不确定性限定。
3. 每项状态为 `pass`、`warning`、`fail` 或 `not-applicable`；总状态按 fail 优先、warning 次之汇总。摘要低匹配只能产生 warning，不能声称来源已被语义证伪。
4. 输出包含 `schemaVersion=1`、`verifierVersion=core-3.4/rule-v1`、检查时间、结构化检查项和固定局限声明。UI 始终称其为“回答规则检查”，明确它不等同于事实证明。
5. `done` 同时返回 Citations 与 Verification。客户端将二者和 Assistant Message 一次写入；PostgreSQL `messages.verification` 使用可空 JSONB，因此旧消息保持兼容，不回填虚构检查结果。
6. 检查面板随消息分支显示：通过时默认折叠，warning/fail 默认展开；刷新、跨设备和切换重新生成版本后仍保留各自结果。
7. API 对结构、版本、四个唯一检查项和 Assistant 角色进行严格校验。浏览器读取时再次进行运行时校验，畸形数据不会进入 UI。

## 后果

- 验证结果稳定、便宜、可测试，不增加模型 Token 消耗，也不会延长到第二次生成调用。
- 规则能发现明确的结构问题，但不能阅读完整网页、证明事实真伪或理解所有跨语言转述；用户仍需打开来源复核。
- 规则版本与数据一起保存。未来改变阈值时提升 `verifierVersion`，不悄悄重解释旧结果。
- Core 3.5 将使用真实问题评测集测量这些规则的误报/漏报，并评测专业回答与模式边界。
