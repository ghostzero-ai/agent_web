# ADR-053 可解释且有预算的主动问候

- 状态：Accepted
- 日期：2026-09-28
- 对应阶段：Phase 5.5

## 背景

任务、简报和书籍推荐已经能由 Worker 在网页关闭后生成并进入 Inbox，但“助手主动找用户聊天”不能等同于再增加一种随机定时任务。没有真实原因、频率上限和停止入口的主动联系容易造成打扰、依赖诱导或负罪感，也难以解释为何此刻触发。

## 决策

1. 独立保存 `ProactivityPreference`，默认关闭。第一阶段只允许 `goal_followup` 和 `checkin`：前者仅使用用户确认、未过期且非敏感的正式目标；后者仅使用用户明确开启的未互动天数，不推断情绪。
2. 确定性策略层依次检查暂停、北京时间安静时段、上一条主动问候是否未读、当日预算、全局冷却期和真实未使用信号。任一检查失败都返回稳定原因且不写 Inbox。
3. Worker 以独立 60 秒默认轮询运行策略。规则通过后，在同一数据库事务创建 InboxItem 与 `ProactivityLedger`；行锁、触发键唯一约束与账本共同保证并发幂等。
4. Ledger 保存原因、触发引用、可见解释和当时策略快照，但不复制目标正文。问候正文只进入 Inbox，并复用既有可失败 Push Delivery。
5. 用户可查看每次联系原因、降低每日数量、延长冷却、暂停一周或关闭单类原因。主动预算不影响用户显式创建的提醒和内容任务。
6. 当前采用确定性的无负罪感模板，不调用模型。未来允许模型润色时，模型只能在规则层已经批准之后改写措辞，不能决定是否联系、提高频率或绕过安静时段。

## 备选方案

- 让模型直接判断何时联系：难以稳定审计，且会增加成本和不可预测行为，因此拒绝。
- 把主动问候建成普通 Task：无法表达上一条未读、跨原因冷却和用户级每日预算，因此拒绝。
- 只发送 Push、不保存 Inbox：设备投递不可保证，会丢失事实记录，因此拒绝。

## 后果

- 主动性是用户可控、可解释和可测试的服务端能力，不依赖页面常驻。
- 低频规则检查增加少量数据库读取，因此使用独立 60 秒默认周期，并以偏好行锁串行化同一用户的评估。
- 第一阶段表达变化较少，但行为边界清晰；情绪理解与危机场景不会混入简单的“久未互动”判断，留给 Phase 5.6 单独评测。
