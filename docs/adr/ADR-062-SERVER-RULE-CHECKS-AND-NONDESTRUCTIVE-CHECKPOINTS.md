# ADR-062：服务端规则检定与非破坏性剧情检查点

状态：已接受（Phase 6.4）

## 背景

Phase 6.3 已能保存可复现骰子和每个剧情节点的状态快照，但通用物品计数不能表达角色生命、属性、状态效果、物品持有者或场景出口。若由模型直接决定检定结果，结果无法审计；若“恢复存档”删除后续回合，又会破坏既有树形历史和用户创作内容。

## 决策

1. 静态 `game_characters` 保存角色设定、数值属性和生命上限；每个 `game_turn.state_snapshot` 保存该分支的当前生命、属性和状态效果。
2. 状态快照加入场景事实、出口和结构化物品定义。物品数量仍位于 Inventory，但存在正数量时必须有定义；非空持有者必须指向分支中的角色。
3. 规则检定由服务端接收角色 ID、属性、难度和骰子请求，从父分支快照读取属性修正，再调用确定性 Dice Tool。结果作为不可变 `rule_check` 事件与回合在同一事务保存。
4. 模型收到的是可信状态与已完成的检定事件，只负责叙事和受限状态补丁，不能决定点数、属性修正或成功等级。
5. `game_checkpoints` 保存名称、备注、目标回合和当时快照。恢复只以乐观锁更新 `active_leaf_turn_id`；不删除、改写或复制任何回合。下一次生成自然以目标回合为父节点形成新分支。
6. Phase 6.3 旧快照在 Repository 读取时标准化：补齐新字段、由当前角色卡播种缺失的运行时角色，并为旧 Inventory 建立最小物品定义。历史数据库行保持不变。

## 结果

- 同一 seed、算法、骰子请求和属性能复现检定，用户可看到修正、难度、差值与结果。
- 分支中的伤害、状态和物品不会泄漏到其他分支，静态角色卡变更也不会重写已有快照。
- 检查点提供熟悉的“存档/读档”体验，同时维持追加式剧情树和可追溯性。
- 完整快照与检查点会增加少量 JSONB 存储；对单用户个人项目可接受，并换来简单、可靠的分支读取。
- 当前仍是规则无关内核。特定桌游规则、自动工具选择和专用 UI 必须通过 Phase 6.5 的娱乐 Activity / 规则包扩展，不进入核心 GameSession 条件分支。

## 未采用方案

- **让模型自行掷骰或判断成功**：不可复现，且模型输出可以与角色属性矛盾。
- **Session 只保存一个可变当前状态**：从历史节点分支时会继承未来或其他分支的数据。
- **恢复检查点时删除后续回合**：会造成不可恢复的数据丢失，也破坏树形对话已确立的因果语义。
- **立即内置完整 D&D/COC 规则**：会把规则系统耦合进核心循环，并抢占 Phase 6.5 对 Plugin API 扩展性的真实验证。
