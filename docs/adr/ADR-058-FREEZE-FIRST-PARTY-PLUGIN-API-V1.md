# ADR-058：冻结第一方 Plugin API v1

- 状态：Accepted
- 日期：2026-09-30
- 阶段：Phase 7.5

## 背景

背书与解题已经在不修改核心 Agent Loop、不中断 Chat/Task、且不直接访问数据库和模型密钥的前提下完成闭环。实践同时暴露了三个不应继续复制的问题：两个 Service 重复定义存储返回与前台上下文；模型/任务 Adapter 通过不断扩大的中央枚举增加用途；插件页按插件 ID 写死 Activity 入口。

## 决策

1. 宿主 Plugin API 从实验版 `0.1.0` 冻结为 `1.0.0`；两个第一方插件声明 `>=1.0.0 <2.0.0` 并升级自身版本到 `1.0.0`，触发一次明确的更新与授权复核。
2. 执行上下文、隔离存储请求/返回、模型调用信封、任务草稿、学习卡内容和来源草稿成为共享的代码级 v1 Schema。
3. `model.generate` 使用稳定的 `{ operation, input }` 信封。具体操作由宿主 Registry 静态注册、绑定插件并独立校验；未知、重复或跨插件借用操作失败。新增第一方操作不再修改中央条件分支。
4. `task.create-draft` 使用稳定的 review intent 与 Activity ID；宿主检查 Activity 归属，只返回草稿，不直接写核心 Task。
5. 跨插件学习卡只冻结带来源的中立草稿格式。插件私有存储继续隔离；未来转移必须由宿主显式导入并由用户确认，不开放插件间直接读写。
6. Activity UI 使用预编译宿主 Registry。插件页从 Manifest Contribution 解析入口，不再识别具体插件 ID；Web 与 Android 路由仍由应用发布物提供。
7. v1 只承诺第一方边界，不宣称第三方沙箱。市场、动态代码、iframe UI、签名分发和动态原生能力继续延后。

## 后果

- Phase 6 可通过新增注册操作和预编译 Activity 接入娱乐模式，不需要修改 Gateway 或核心 Agent Loop。
- v1 的破坏性变更必须提升宿主主版本；兼容的新操作可在 1.x 增加。
- 用户需要审核两个插件的 1.0.0 更新并重新确认旧授权，但原有隔离数据不会删除。
- 中立学习卡 Schema 解决格式与来源问题，不等于已经建立共享卡片数据库。
